# “人类调度”产品设计文档

## 1. 文档目的

本文档用于定义“人类调度”的产品定位、核心能力、交互方式和第一阶段实现范围，为后续 AI 生成技术方案、原型、代码和测试任务提供基础材料。

本文档的默认读者包括：产品经理、设计师、前端/客户端工程师、后端工程师以及负责继续拆解任务的 AI。

---

## 2. 产品概述

### 2.1 产品名称

**人类调度**

### 2.2 一句话定义

一个以 AI 为“老板/调度者”的个人工作管理工具：人类用自然语言汇报工作，AI 负责收集、拆解、安排、提醒、追问和验收。

### 2.3 核心愿景

让用户不必维护复杂的待办清单，而是像向老板汇报一样与 AI 对话：

- 告诉 AI 自己有哪些工作；
- 随时询问“我现在该做什么”；
- 汇报刚刚完成了什么；
- 接收 AI 自动拆解后的任务和下一步行动；
- 在规定时间被提醒和检查；
- 同时推进多个工作，但始终知道当前最该做什么。

### 2.4 产品定位

“人类调度”不是传统待办事项工具，也不是单纯的聊天机器人，而是一个具备任务记忆、任务结构化、日程调度、主动提醒和进度监督能力的 AI 工作管家。

---

## 3. 目标用户与使用场景

### 3.1 目标用户

第一阶段聚焦以下用户：

- 独立工作者、自由职业者；
- 学生、研究者、创作者；
- 需要自我管理的远程工作者；
- 同时推进多个项目、容易遗忘下一步行动的人；
- 希望获得外部压力和明确工作节奏的人。

### 3.2 典型场景

#### 场景 A：快速收集工作

用户输入：“这周要完成官网首页、给客户发报价、整理上个月的发票，还要准备周五的汇报。”

AI 应当识别出多个工作，询问必要的截止时间和优先级，并建立结构化任务。

#### 场景 B：不知道现在该做什么

用户输入：“我现在做什么？”

AI 综合截止时间、优先级、预计耗时、上下文切换成本和当前工作状态，给出一个明确的首要任务，以及可立即执行的第一步。

#### 场景 C：汇报已完成工作

用户输入：“报价单已经发给客户了，官网首页做完了首屏。”

AI 更新对应任务状态，识别“官网首页”仍未完成，并给出下一步。

#### 场景 D：AI 布置工作

AI 主动提示：“你在 14:00 前需要完成客户报价。现在开始，先补齐报价单中的交付范围，完成后向我汇报。”

#### 场景 E：工作拖延或失联

用户超过预设时间没有反馈，AI 发送追问：“任务已经到点。说明原因：已完成、遇到阻塞、需要重新安排，还是你在逃避？”

#### 场景 F：多个工作并行

用户同时处理“官网项目”“论文”“家庭事务”。AI 应维护多个项目上下文，在需要时帮助用户切换，并防止任务相互混淆。

## 4. 产品原则

### 4.1 自然语言优先

用户不应被迫先填写复杂表单。先允许用户用自然语言表达，再由 AI 提取和结构化。

### 4.2 任务必须落地

每次对话尽量产生明确结果：创建任务、更新状态、安排时间、确认阻塞或给出下一步，而不是只进行泛泛聊天。

### 4.3 AI 负责调度，人类负责执行

AI 可以安排、提醒、追问和验收，但不应假装已经完成用户没有确认的工作。

### 4.4 监督要有压力，但不能失控

默认语气可以强势、命令式、像严厉老板或奴隶主式调度者，但不得出现人身侮辱、歧视、威胁现实伤害、恶意羞辱或诱导危险行为。用户应能调整强度。

### 4.5 先给一个明确动作

当用户不知道做什么时，优先给出一个 5～30 分钟内可开始的具体动作，而不是罗列一大堆任务。

### 4.6 任何自动化都可解释、可暂停

定时提醒、自动重排和强势追问都应可配置、可暂停、可查看原因。

## 5. 交互形态决策

### 5.1 推荐形态：桌面常驻“小窗 + 系统托盘 + 通知弹窗”

推荐采用桌面端优先，组合三个入口：

1. **系统托盘常驻**：展示当前任务状态，随时唤起。
2. **悬浮小窗**：默认是一个窄小的 AI 对话窗口，适合快速汇报、问“现在做什么”和确认完成。
3. **主动通知弹窗**：到点、逾期、任务切换或 AI 需要确认时弹出。

### 5.2 为什么不只做完整主界面

用户使用频率高、单次操作短，核心动作是输入一句话或确认一件事。完整看板适合复盘，但不适合作为日常主入口。小窗能降低打开成本，也更符合“老板随时叫你”的产品隐喻。

### 5.3 窗口层级

#### 一级：悬浮调度窗

- 当前正在执行的任务；
- AI 的一句指令；
- 倒计时/截止时间；
- 单行自然语言输入框；
- “完成”“阻塞”“延期”“展开详情”快捷按钮。

#### 二级：完整工作台

- 今日调度；
- 所有任务；
- 项目；
- 日历/时间块；
- 监督记录；
- AI 设置；
- 数据导出。

#### 三级：设置与配置

- 模型 API 配置；
- 语气和监督强度；
- 通知策略；
- 工作时间；
- 数据存储和隐私；
- 快捷键。

### 5.4 推荐默认快捷键

- `Ctrl/Cmd + Shift + Space`：唤起调度小窗；
- `Ctrl/Cmd + Enter`：发送消息；
- `Alt + 1`：标记当前任务完成；
- `Alt + 2`：标记为阻塞；
- `Esc`：关闭小窗但保持后台运行。

## 6. 核心功能范围

### 6.1 自然语言工作收集

用户可以输入：

- “我今天要写完方案”；
- “下周前把网站上线”；
- “提醒我下午联系张三”；
- “客户反馈还没来，先记着”；
- “刚刚把第三章改完了”；
- “这个任务先别催，等对方回复”。

AI 需要从输入中识别：

- 新任务；
- 已完成任务；
- 任务更新；
- 截止时间；
- 开始时间；
- 优先级；
- 依赖关系；
- 阻塞原因；
- 提醒要求；
- 用户偏好。

如果信息不足，AI 只追问最关键的问题，不应一次询问十个字段。

### 6.2 任务拆解

AI 将模糊目标拆解为可执行任务：

```text
目标：完成产品设计方案

任务树：
1. 明确目标用户和使用场景
2. 梳理核心功能
3. 设计任务数据结构
4. 输出交互流程
5. 评审并修改文档
```

拆解规则：

- 每个子任务应该能在一次工作时段内完成；
- 子任务应以动词开头；
- 能判断完成与否；
- 标注预计耗时；
- 标注前置依赖；
- 子任务过多时先给出第一层拆解，用户要求后再展开。

### 6.3 调度与优先级

AI 根据以下因素安排工作顺序：

- 截止时间紧迫度；
- 用户指定的优先级；
- 任务依赖关系；
- 预计耗时；
- 当前剩余时间；
- 用户当前上下文；
- 工作时间和休息时间；
- 切换成本；
- 任务是否已经拖延。

第一阶段采用可解释的规则评分，不要求一开始就做复杂的智能排程。

建议评分模型：

```text
调度分 = 截止紧迫度 × 40%
       + 用户优先级 × 25%
       + 依赖阻塞影响 × 20%
       + 拖延程度 × 10%
       + 当前上下文匹配度 × 5%
```

AI 每次只需要明确回答：

1. 现在做什么；
2. 为什么现在做它；
3. 做到什么算完成；
4. 多久后回来汇报。

### 6.4 定时监工

支持以下监督类型：

- 开始提醒：到时间要求开始；
- 中途检查：工作一段时间后询问进度；
- 截止提醒：到截止时间前提醒；
- 逾期追问：超过截止时间询问状态；
- 完成验收：用户说完成后要求结果或证据；
- 日终复盘：总结完成、未完成和明日安排。

每次监督都应产生一条监督事件，记录发送时间、用户响应和后续动作。

### 6.5 多任务并行

用户可以同时拥有多个活跃任务，但 AI 需要区分：

- 当前任务：正在做的事情；
- 排队任务：准备做但尚未开始；
- 等待任务：等待他人、资料或外部结果；
- 阻塞任务：无法继续，需要决策或帮助；
- 低频任务：重要但不应频繁打断。

AI 默认限制同时处于“执行中”的任务数量，建议默认为 1 个，允许用户配置为 2～3 个。超过限制时提醒用户：“你同时开了 5 个任务，这不是并行，是分心。选择一个先完成。”

### 6.6 工作完成确认

当用户说“做完了”，AI 需要：

1. 尝试匹配当前任务；
2. 更新任务状态；
3. 判断是否存在剩余子任务；
4. 如有必要，要求简短验收信息；
5. 给出下一个工作安排。

示例：

```text
用户：官网首页做完了。
AI：已记录“官网首页首屏”完成。还有两个子任务未完成：移动端适配、埋点检查。
下一项：现在处理移动端适配，预计 45 分钟。完成后向我汇报。
```

### 6.7 项目与上下文

任务归属于项目，项目可以拥有独立的：

- 目标；
- 截止日期；
- 任务列表；
- 相关人/组织；
- 工作规则；
- AI 语气；
- 参考资料；
- 当前进度。

### 6.8 语气与监督强度

建议提供五档监督风格：

1. **温和助理**：提醒和建议为主；
2. **严格教练**：明确要求和复盘；
3. **老板模式**：命令式、追问结果；
4. **高压调度**：频繁检查、强调截止时间；
5. **角色扮演模式**：强烈的奴隶主式措辞，但仍受安全边界约束。

用户可以对特定项目单独设置风格。

语气示例：

```text
老板模式：
“现在停止整理无关信息，先完成报价单。30 分钟后汇报结果。”

角色扮演模式：
“你的下一项工作已经下达：完成报价单中的交付范围。不要转移注意力，完成后立刻回来报告。”
```

不允许的表达包括现实伤害威胁、针对身份的侮辱、鼓励过劳、羞辱性攻击和将 AI 指令伪装成不可撤销的现实命令。

## 7. 关键用户流程

### 7.1 首次启动

1. 用户打开应用；
2. 选择 AI 服务商或自定义 API；
3. 填写 Base URL、API Key、模型名称；
4. 点击连接测试；
5. 选择工作时区、工作时间、默认监督强度；
6. 输入第一批工作；
7. AI 生成今日调度计划；
8. 用户确认或修改计划。

### 7.2 添加任务

```text
用户：这周要做完官网改版，今天先把首页结构确定下来。
AI：收到。我拆成两个层级：
    项目：官网改版，本周完成
    今日任务：首页结构确定，预计 90 分钟
    你希望今天几点前完成？
用户：下午 5 点前。
AI：已安排。16:00 提醒你进入收尾，17:00 进行完成检查。
```

### 7.3 查询当前任务

```text
用户：我现在该做什么？
AI：现在执行“确定官网首页结构”。
原因：今天 17:00 截止，且它是官网改版的下一项阻塞任务。
第一步：打开现有首页，列出必须保留、删除和新增的模块。
45 分钟后回来汇报。
```

### 7.4 汇报完成

```text
用户：首页结构确定了。
AI：已完成“确定官网首页结构”。请确认：是否已经形成可供评审的文档或草图？
用户：有，放在设计文档里了。
AI：验收通过。下一项是“补齐首页文案”，今天 18:00 前完成，预计 40 分钟。
```

### 7.5 处理阻塞

```text
用户：我做不了，缺客户的品牌资料。
AI：已将任务标记为“等待外部资料”。现在布置替代工作：
1. 给客户发送资料请求；
2. 在等待期间整理首页内容框架。
先完成第 1 项，10 分钟后汇报是否已发出。
```

## 9. 大模型接入设计

### 9.1 必须支持的配置项

- Provider 名称；
- API Base URL；
- API Key；
- 模型名称；
- API 协议类型；
- 请求超时；
- 最大输出长度；
- 温度；
- 是否启用流式输出；
- 是否启用结构化输出。

### 9.2 首期协议兼容策略

首期建议优先兼容 OpenAI 风格接口，同时保留 Provider 适配层，便于接入其他兼容服务。

建议抽象接口：

```text
ModelProvider
  - testConnection()
  - chat(messages, options)
  - chatStructured(messages, schema, options)
  - streamChat(messages, options)
```

### 9.3 API Key 安全

- API Key 默认只在本机保存；
- 优先使用操作系统凭据管理器或加密存储；
- 界面中只显示部分掩码；
- 日志禁止输出 API Key；
- 用户可以随时删除本地配置；
- 明确提示：自定义 API 可能产生第三方费用，费用由用户自行承担。

### 9.4 AI 输出约束

大模型不能直接自由修改数据库。建议采用“意图识别 + 结构化动作”的方式：

```json
{
  "reply": "已安排今天 17:00 前完成首页结构。",
  "actions": [
    {
      "type": "create_task",
      "title": "确定官网首页结构",
      "project": "官网改版",
      "due_at": "2026-09-23T17:00:00+08:00",
      "estimated_minutes": 90,
      "priority": "high"
    }
  ],
  "follow_up": {
    "enabled": true,
    "after_minutes": 45,
    "reason": "中途进度检查"
  }
}
```

系统执行动作前应进行：

1. JSON Schema 校验；
2. 权限和范围校验；
3. 时间合法性校验；
4. 冲突检查；
5. 对高影响操作要求用户确认。

## 11. 调度与提醒规则

### 11.1 默认规则

- 新任务如果有明确日期，自动创建提醒；
- 没有截止时间的高优先级任务，AI 先询问日期或安排今天的工作块；
- 当前任务超过预计时间仍未汇报，触发一次检查；
- 逾期后默认每 30 分钟最多提醒一次，避免通知轰炸；
- 用户连续忽略三次提醒，自动进入“需要重新安排”状态；
- 休息时间不发送普通提醒，紧急任务除外；
- AI 不自动把任务安排到已经过去的时间；
- 任务被标记为等待后，不持续催促用户，改为设置下一次检查时间。

### 11.2 通知渠道

第一阶段：

- 应用内通知；
- 桌面系统通知；
- 小窗红点/状态变化。

后续可扩展：

- 邮件；
- 手机推送；
- 企业聊天工具；
- 日历事件。

## 12. MVP 范围

### 12.1 MVP 必须实现

- 桌面端小窗；
- 系统托盘常驻；
- 自然语言对话；
- 自定义 API Base URL、API Key、模型；
- 兼容 OpenAI 风格接口；
- 创建、更新、完成、延期、阻塞任务；
- AI 任务拆解；
- 今日任务列表；
- 当前任务推荐；
- 基础定时提醒；
- 监督事件记录；
- 多项目；
- 五档监督语气；
- 本地数据存储；
- 数据导出 JSON/Markdown。

### 12.2 MVP 不做

- 多人协作和团队权限；
- 复杂的企业审批；
- 自动操作第三方软件；
- 自动代替用户发送重要外部消息；
- 手机原生客户端；
- 复杂统计报表；
- 过度依赖模型自主决策的全自动代理。

## 13. 技术实现建议

### 13.1 客户端

推荐使用跨平台桌面框架，例如 Electron 或 Tauri。

需要支持：

- 系统托盘；
- 全局快捷键；
- 桌面通知；
- 开机启动；
- 窗口置顶；
- 本地数据库；
- 后台定时任务。

如果优先考虑包体积、资源占用和安全性，可优先评估 Tauri；如果需要更快验证和更丰富的 JavaScript 生态，可优先评估 Electron。

### 13.2 本地服务层

建议将能力拆成：

- `ConversationService`：对话与上下文；
- `IntentParser`：从自然语言提取意图；
- `TaskService`：任务增删改查；
- `TaskDecomposer`：任务拆解；
- `Scheduler`：调度；
- `SupervisionService`：监工事件；
- `NotificationService`：通知；
- `ProviderService`：模型供应商适配；
- `SettingsService`：设置和凭据。

### 13.3 存储

MVP 建议使用 SQLite：

- 支持本地优先；
- 查询任务和事件方便；
- 适合离线使用；
- 后续可增加云同步层。

### 13.4 时间处理

- 所有内部时间使用带时区的 ISO 8601；
- 显示时使用用户本地时区；
- 自然语言日期解析必须考虑“今天、明天、下周五”等相对时间；
- 发生歧义时必须确认具体日期。

## 14. AI 行为规范

### 14.1 AI 每次响应优先包含

- 当前理解；
- 已执行的动作；
- 下一步指令；
- 时间要求；
- 用户需要确认的内容。

### 14.2 AI 不应做的事情

- 未经确认删除任务或大量重排日程；
- 假设用户完成了任务；
- 把模糊愿望直接伪装成确定计划；
- 在休息时间无休止催促；
- 用羞辱、威胁或现实伤害语言逼迫用户；
- 暗中调用未配置的 API；
- 将 API Key、完整对话或私人数据发送到未告知的服务。

### 14.3 失败时的降级策略

当模型调用失败：

1. 明确告知模型不可用；
2. 保留本地任务和提醒能力；
3. 允许用户手动创建或完成任务；
4. 提供重试和切换模型入口；
5. 不丢失用户刚刚输入的内容。

## 15. 成功指标

### 15.1 MVP 产品指标

- 用户从输入一句话到任务创建的成功率 ≥ 90%；
- 任务状态识别正确率 ≥ 90%；
- 用户能在 5 秒内打开调度小窗；
- 提醒送达成功率 ≥ 99%；
- AI 推荐的下一项任务被用户接受或修改的比例 ≥ 60%；
- 用户一周内至少使用 3 次自然语言汇报；
- 用户能在 10 秒内完成“完成/阻塞/延期”操作。

### 15.2 体验指标

- 用户不需要维护复杂字段；
- 用户能快速知道当前第一优先级；
- 用户能理解 AI 为什么安排这项工作；
- 用户不会因通知过多而关闭监督功能；
- 语气有压力但不会让用户产生被攻击或被骚扰的感受。

## 16. 风险与对策

### 风险 1：AI 误解任务

对策：重要动作前显示结构化摘要；允许一键撤销；保留变更历史。

### 风险 2：提醒过多导致反感

对策：通知频率上限、免打扰时段、忽略次数检测、监督强度设置。

### 风险 3：强势语气越界

对策：语气模板分级、安全过滤、禁止现实威胁和身份攻击、允许一键切换温和模式。

### 风险 4：API Key 泄露

对策：本地加密存储、脱敏日志、连接测试不回显密钥、用户可删除配置。

### 风险 5：用户把 AI 当作绝对权威

对策：明确 AI 是调度工具；关键安排提供修改、暂停和拒绝入口；所有自动安排可追溯。

### 风险 6：用户同时开启太多任务

对策：设置并行任务上限；主动提示上下文切换成本；优先推动一个任务完成。

## 19. MVP 验收标准

一个新用户安装后，应能完成以下闭环：

1. 配置自己的 AI API；
2. 输入一段包含多个工作的自然语言；
3. AI 将其拆解成结构化任务；
4. 用户确认今天先做哪一项；
5. AI 在指定时间发出提醒；
6. 用户用自然语言汇报完成或阻塞；
7. 系统正确更新任务状态；
8. AI 给出下一项工作；
9. 用户能在工作台看到全部项目、任务和监督记录；
10. 用户能暂停、修改或关闭 AI 监督。

如果这条闭环稳定可用，“人类调度”就具备了第一个可验证产品版本。

## 20. 面向公开免费发布的产品化要求

为了让产品可以免费提供给更多用户，桌面端需要优先具备以下基础能力：

- 本地优先：没有 API 配置时仍可创建任务、调整状态和使用固定提醒；
- 可迁移：支持导出和导入 JSON 备份，导出文件默认不包含 API Key；
- 可恢复：删除任务和提醒采用二次确认，批量清空继续保留明确确认步骤；
- 可理解：设置页明确说明 API Key 保存位置、第三方模型费用由用户承担、模型不可用时会降级到本地规则；
- 可支持：设置页提供“请作者喝咖啡”入口，赞助链接由发布者配置，不把支付平台写死在核心逻辑中；
- 可扩展：支持搜索和状态筛选，避免任务量增长后工作台失控；
- 可隐私：日志不输出 API Key，备份和错误提示不泄露密钥。

公开发布前还应补充隐私政策、开源许可、问题反馈入口、版本更新说明，以及针对通知频率、API 费用和强势角色边界的用户说明。
